① 集成 API（北向） REST / JSON · v1 frozen
面向采购平台 / ERP / 上游业务系统的标准集成面：票据识别、案件查询、证据追溯、事件回调。
POST /v1/invoices:recognize

提交供应商采购发票进行识别与案件化处理。同步模式：仅走直读快速路径（数电票 XML 直读 / PDF 文本层直读），P95 < 3s 内返回完整 InvoiceCase； 其余情况自动转异步模式：立即返回 caseId，处理完成后通过 callback_url Webhook 回调。 支持 multipart/form-data（文件直传）或 application/json（file 引用）两种请求体。

Request · application/jsonv1
{
  "file": {
    "ref": "oss://intake/2026/10/21/INV-CN-0387.xml",
    "mime_type": "application/xml",
    "sha256": "9f2c…e41a"
  },
  "instance": "CN",            // "CN" | "OS" 双实例路由
  "doc_type_hint": "e_invoice", // 可选：数电票 / VAT Invoice / Credit Note
  "po_ref": "PO-2026-00871",   // 可选：关联采购订单，触发 PO 三单匹配
  "callback_url": "https://erp.customer.com/hooks/invoice-case",
  "options": {
    "sync_fast_path_only": true, // 超时未直读即转异步
    "verify_authenticity": true  // 是否触发授权查验（Provider SPI）
  }
}

status 状态机六值（与蓝图 §4.7 一致）： RECOGNIZED VERIFYING NEEDS_REVIEW INVESTIGATING RESOLVED BLOCKED
GET
/v1/cases/{caseId}
案件状态查询：返回完整 InvoiceCase 快照（status / facts / checks / nextAction / 时间线摘要），用于上游系统轮询异步识别结果与案件生命周期跟踪。支持 ?view=summary|full。
GET
/v1/cases/{caseId}/evidence
字段级证据链查询：逐字段返回 value / source / confidence / page / bbox / raw_text / rule / model_version / provider，支撑「可解释识别、拒绝黑盒 AI」的审计要求。支持 ?field=total.gross_amount 精确过滤。
Webhook 回调事件
异步案件在状态跃迁时向 callback_url 推送事件；消费方须返回 2xx，否则按指数退避重试（最多 8 次）。
事件类型 触发时机 Payload 关键字段 典型消费动作
case.recognized 识别完成，案件进入 RECOGNIZED / NEEDS_REVIEW caseId, status, facts, checks 拉取案件详情，驱动上游流转
case.blocked 命中红线规则（重复票 / 验签失败等），案件 BLOCKED caseId, blockReason, ruleId, evidenceRef 冻结下游建档 / 付款前置流程
case.resolved 人工复核或自动路径完成，案件 RESOLVED caseId, resolution, operator, actionTrailRef 触发目标系统建档（Adapter API）
check.failed 单项校验失败（不一定整案拦截） caseId, checkName, result, variance 提示业务侧关注差异明细
🔐
签名校验（X-Signature）：每个回调请求携带 X-Signature: sha256=<hex> 头，值为 HMAC-SHA256（密钥 = 订阅时下发的 webhook secret，消息体 = 原始 JSON 字节）。消费方必须验签后再处理；另附 X-Event-Id 用于幂等去重。

② MCP Server（北向 · Agent 生态） MCP Protocol · v1 frozen

在集成 API 之上的 MCP（Model Context Protocol）协议封装：SAP Joule 与第三方 Agent 可作为 MCP Client 直接调用平台工具，无需理解内部 REST 细节。

⚠️
受控边界（与蓝图 §10 一致）：只读工具任意调用、无副作用；写工具（识别提交 / 案件处置）必须携带人工确认 token，AI 禁止静默执行业务写操作 —— 放行 / 挂起 / 退回全部走人工确认 + 全量审计留痕。

③ Provider SPI（南向） 插拔契约 · v1 frozen

新增 OCR / 查验 Provider（百望云、诺诺、客户自有 OCR、私有化 VLM、海外 e-invoicing 等）只需实现 SPI 并注册路由，不改平台内核。这是「可插拔 Provider 编排」定位的契约基础。

最小实现契约 3 个方法 · verify 仅查验类 Provider 必需
capabilities()
声明能力集：支持的票种 / 地区 / 文件格式、识别或查验类型、并发与 SLA，供路由引擎调度。
recognize(payload)
接收文件引用与实例上下文，返回归一化格式的字段识别结果（含证据）。
verify(payload)
查验类可选：授权渠道验真（数电票验签 / 税局查验 / 海外 e-invoicing 核验），返回可留存回执。
结果归一化格式 所有 Provider 输出统一转为该结构后进入平台内核

路由 / 降级配置片段 YAML · 与 Provider 编排页同一口径
routing/cn-e-invoice.yamlSPI v1
route: cn_e_invoice_recognize
strategies:
  - provider: xml_direct            # 数电票结构化原件优先直读（免 Provider）
    priority: 10
    condition: mime_type == "application/xml"
  - provider: bwyun-cn
    priority: 20
    threshold: 0.85                 # 字段平均置信度低于阈值 → 降级
    fallback: next
  - provider: nuonuo-cn
    priority: 30
    threshold: 0.85
    fallback: human_review          # 双 Provider 均不达标 → 强制人工
cross_check:
  enabled: true
  require_different_source: true    # 异源交叉核验：金额类字段须由不同来源 Provider 复核
  fields: [total.gross_amount, total.tax_amount]

④ Adapter API（东向） 建档契约 · v1 frozen

新目标系统（SAP Ariba / Oracle Payables / Coupa / S4 HANA / 自研应付）按 Adapter 模板开发，复用平台统一 Schema 出口 —— 内核只产出标准 InvoiceCase，字段映射差异全部收敛在 Adapter 层。 建档契约以 Ariba cXML InvoiceDetailRequest 为例（字段级映射细则 ⏳ 待确认 · H24）。

cXML InvoiceDetailRequest 骨架示例 统一 Schema → Ariba 建档出口
adapters/ariba/outbound/InvoiceDetailRequest.xmlcXML 1.2.040
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE cXML SYSTEM "http://xml.cxml.org/schemas/cXML/1.2.040/InvoiceDetailRequest.dtd">
<cXML payloadID="invoice-hub-INV-2026-00125@ariba" timestamp="2026-10-21T09:32:10+08:00">
  <Header>
    <From><Credential domain="NetworkID"><Identity>invoice-hub-cn</Identity></Credential></From>
    <To><Credential domain="NetworkID"><Identity>ariba-buyer-an12345</Identity></Credential></To>
    <Sender><Credential domain="NetworkID"><Identity>invoice-hub-cn</Identity>
      <SharedSecret>${ARIBA_SHARED_SECRET}</SharedSecret></Credential></Sender>
  </Header>
  <Request deploymentMode="production">
    <InvoiceDetailRequest>
      <Contact addressID="supplier-8871" role="supplier">
        <Name xml:lang="zh-CN">北京中科华创科技有限公司</Name>
      </Contact>
      <!-- 映射①：InvoiceCase.facts.invoiceAmount → InvoiceDetailRequest 头金额 -->
      <InvoiceDetailHeader invoiceDate="2026-10-18" invoiceID="24442000000387">
        <Total><Money currency="CNY">113000.00</Money></Total>
        <!-- 映射②：facts.taxAmount + evidence(rule=tax_code_mapping) → Tax 节点 -->
        <Tax><Money currency="CNY">13000.00</Money>
          <Description xml:lang="zh-CN">增值税 13%</Description></Tax>
        <!-- 映射③：po_ref → OrderReference（三单匹配依据，缺省走 non-PO 流程） -->
        <OrderReference orderID="PO-2026-00871"/>
      </InvoiceDetailHeader>
    </InvoiceDetailRequest>
  </Request>
</cXML>

Adapter 开发流程 4 步 · 第三方凭契约文档可独立完成（L2 判定口径）
1模板 fork
从 adapters/ 模板库 fork 目标系统 Adapter 骨架，继承统一 Schema 出口与鉴权、重试、审计基座。
2字段映射
按映射模板配置 InvoiceCase → 目标报文字段（含税额口径、币种、供应商主数据对照），声明必填与容差。
3沙箱联调
基于 ariba-mock 演示资产在沙箱回放真实案件样例，验证报文结构、异常回执与幂等重发。
4契约测试
运行 contracts/ 契约测试套件（结构 / 语义 / 版本兼容三层），全部通过后方可注册上线。
